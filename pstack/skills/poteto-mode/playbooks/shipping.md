### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, a `delegate_task` child on the counterpart of the code author's family (the Counterparts list in the role file, `~/lim-v2/AGENTS.md` or `~/lim-v2/CLAUDE.md`) and never the author, in its own worktree per poteto-mode's Subagents section, runs the change the way a user would through the project's verify skill, which its brief names, parent against head, and posts its verdict on that PR as a comment line `pstack-verdict: <PASS|PASS+NOTES|FAIL> head=<head sha> base=<merge-base sha> by=<model>`, with its findings below. The merge gate reads that line. The brief also names the repo's merge brief, `.agents/merge-brief.md`, because the verdict must cover what it requires. When the PR has a plan (`playbooks/multi-phase-plan.md`), the brief names the plan file and the PR's section. The brief points the verifier to this step, `~/.agents/skills/poteto-mode/playbooks/shipping.md` step 1, for the verdict's format, and does not copy it. Under the `pstack-verdict:` line, the verdict then lists every required box of that section, by the id `check-plan.mjs` prints, one line each: `box <id>: done`, `box <id>: n/a. <reason>`, or `box <id>: skipped. <what did not run>`. A box carried by step 3's rule is done, with the verdict it came from. The verdict also lists a lane carried across a changed patch as a shortcut. A skip counts only when the lead accepts it with a reason, or defers it to an owner, on the merge gate run that lands the PR (step 4). The lead accepts a skip only for a box that does not apply, and defers a box whose work is owed, naming its owner, a Linear id or an open workflow step. A box whose bar changed after an earlier verdict reads `box <id>: changed. <who accepted the change>, <why>`. The gate counts it only with both. Every agent posts as the same GitHub account, so no PR comment can waive a skip. Until the lead accepts or defers it, the gate refuses the verdict. A finding outside the plan's boxes stays the lead's call. The lead checks it, and fixes it or says on the PR why it does not block. The lead writes its own call on a `pstack-ruling: head=<head sha> by=<the lead's model>` line and names the reports it rests on. Only the verifier writes a `pstack-verdict:` line. A ruling never turns a FAIL into a pass, so a FAIL clears only through the verifier's next verdict. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. So every verdict records the head it verified and that head's merge base with the PR's base branch, both taken when verification runs. Before trusting an older verdict, compare the whole-PR change it saw with the current one. Run `~/.agents/skills/poteto-mode/scripts/verdict-hash.sh <saved-merge-base> <verdict-head>` and `~/.agents/skills/poteto-mode/scripts/verdict-hash.sh <current-merge-base> <current-head>`. The verdict carries only when both succeed and print the same hash. A failure means it does not carry. Never hash `git diff` or `git patch-id` output by hand, because each can match code that runs differently, and the script is where those cases are tested. Use the saved merge base, never one recomputed from today's base branch, because a rebase moves it. Matching IDs carry the verdict to the current head. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both heads apart from noise. Noise is a difference that also shows up between two builds of the verdict head, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it unless it carries as a shortcut below, and re-verify anything else that drifted. The verifier may shorten re-verification after a rebase or a small change, but never skips it. The verifier reruns the merge brief's checks at the new head and reviews what changed since the earlier verdict, in the PR's own change (`git range-diff`) and in trunk under it. It may carry an earlier passing lane instead of rerunning it, even one with no build output, when nothing that changed reaches what the lane runs. The re-verification section of the project's verify skill, when it has one, says which changes reach which lanes. A change to code, config or a dependency the lane runs, or to the verify skill's steps for that lane, forces a rerun. The verdict lists each shortcut under its `pstack-verdict:` line as `shortcut <id>: <what was not rerun, and the verdict it carries>. <why nothing that changed reaches it>`. `<id>` is the box id when it shortens a box, such as `live-1`, and otherwise a lowercase slug with hyphens. The lead accepts each one on the gate run that lands the PR (step 4), or has it rerun.
4. **Land bottom-up, one PR at a time, only through the merge gate.** Always merge the run's lowest unmerged PR with `~/.agents/skills/poteto-mode/scripts/merge-gate/merge-gate --repo <owner/name> --pr <pr>`, adding `--plan <plan file> --plan-pr <PR id>` when the PR has a plan. `--repo` works from any directory, with or without a checkout of the repo. The gate prints the repo's merge brief first, so read it. A PR whose body declares its plan (`pstack-plan: <plan file> pr=<PR id>`, per `playbooks/opening-a-pr.md`) is checked against that plan without the flags, and the gate refuses when the plan it names is missing or differs from the one passed. With no plan either way, it says no plan was checked. Never run `gh pr merge` or arm auto-merge yourself. At the PR's current head, the gate checks that every check passed (Bugbot is not waited on), no review thread is open, the verdict covers the exact code (step 3's hash), the verdict lists every required box from the plan, the lead accepted or deferred each skipped one and accepted each shortcut, Codex has reviewed that head, and Lee approved the exact text of any AGENTS.md or CLAUDE.md change. Lee approves in chat, in the T3 thread where an agent showed the exact text. That agent then posts one PR comment with the gate's `lee-approves-instruction-files: <hash>` line, an `approved-in: <T3 thread id>` line and Lee's words quoted, and never posts it without that approval. The hash ties the approval to that text, so any later edit needs Lee's yes again. If anything is missing it merges nothing and prints what is missing and what to do. Otherwise it merges, reads the PR back, and fails unless it reads merged into trunk. To accept a skipped box, add `--accept-skip <id>=<reason>` once per box. To defer one whose work is owed, add `--defer <id>=<owner>`, where the owner is a Linear id or a workflow step written `<thread id>/w<n>.<n>`. To accept a shortcut the verdict lists, add `--accept-shortcut <id>=<reason>`. To merge past a missing CI check, an open review thread, or a missing Codex review, add `--waive <checks|threads|codex>=<reason>`. The verdict on the exact code and the instruction-file approval cannot be waived. The gate posts the waivers, deferrals and accepted shortcuts on the PR before it merges and records them in its run log. `--check` runs the same checks without merging. `merge-gate audit [--repo <owner/name>] [--since <YYYY-MM-DD>]` lists merges that have no gate receipt and saves the table under `merge-gate/audit/` in the pstack store. It also lists each skip, deferral, shortcut and waiver the lead accepted on a gated merge, with its reason or owner. It lists a gap that `--known <owner/name>#<pr>@<head>` names apart from new ones, and one that `--historical <owner/name>#<pr>@<head>=<reason>` settles as historical, never as receipted. In each repo it audits, the window reaches back to the oldest gap that the latest earlier audit file listing it left unresolved, until `--historical` settles that gap. `--unreachable <host>` names a host whose receipts it could not read. It exits 0 when every merge is receipted or historical, 1 on any new or known gap, and 2 on a usage or read error. Run it at each job's close-out. It also runs daily, and the retro round reads its results. The gate squash-merges by default. Pass `--method merge` when the repository requires merge commits, as `liminal-ai/t3code-v2`'s `FORK.md` does. The gate works through `gh`, so on Origin stop and report. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's diff rule decides whether the verdict survives. Run the gate on it once its checks pass.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On both forges, keep the fallback heartbeat per the Waking and polling section of the role file (`~/lim-v2/AGENTS.md` or `~/lim-v2/CLAUDE.md`), because a watch ends on merge and the heartbeat is what notices it. On GitHub, arm `watch_pull_request` on the run's current bottom PR. On each wake, run the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top> --status-only`), read the PR back as step 4 says, and re-arm the watch on the new bottom PR, until the ceiling reads merged. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.
