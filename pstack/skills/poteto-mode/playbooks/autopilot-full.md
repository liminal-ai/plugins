### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The diff rule in `playbooks/shipping.md` step 3 can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each owner is a `delegate_task` child on the `cloud workers` line in the role file (`~/lim-v2/AGENTS.md` or `~/lim-v2/CLAUDE.md`), or local in its own worktree when it needs this machine. It builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the `deslop` skill (`/deslop`)) and the `/no-comments` pass, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   An owner babysits its own PR without `watch_pull_request`, because a child cannot watch a PR, a cloud VM has no T3 tools, and an owner that ends its turn to report ends its task. A local owner polls with the bare `~/.agents/skills/poteto-mode/scripts/watch-pr/watch-pr` on GitHub. A cloud owner has no pstack install, so it polls `gh pr view <pr> --json state,mergeStateStatus,reviewDecision,statusCheckRollup` for checks and pages the review threads with `gh api graphql --paginate` over `pullRequest.reviewThreads(first: 100, after: $endCursor)` with `pageInfo { hasNextPage endCursor }` (`isResolved`, and each comment's author and body), because `gh pr view --comments` leaves out inline findings such as Bugbot's. It triages every unresolved thread before it reports merge-ready. On Origin an owner uses `origin pr checks <pr> --watch`, so a cloud owner on Origin needs the Origin CLI on its VM, or the owner runs local.

   An owner reports every head as a PR comment, `CODE-READY <sha>` for the code-ready head and the same form for each later head and merge-ready, and never by ending its turn. The comment is the record, not the wake, because T3's PR watch ignores comments from its own GitHub account and owners post as that account. So a local owner also sends the same line to your thread with `t3_thread_send` (mode `queue`), and its brief names your thread id. While any cloud owner is out, keep a 10-minute poll of those owners' PRs for new report comments (a `schedule_task` interval whose `scheduledTaskId` you keep), and delete it when none is left. Act on a report only when the account owners post as wrote it and its SHA is the PR's current head, because anyone who can comment can write the same text.

   Assume the VM dies. Name the run with a short slug before the first spawn. Each owner keeps a `decisions.tsv` trail per the **show-me-your-work** skill under `autopilot/<run-slug>/<repo>/<branch>/` in the pstack store (the `pstack store` line in the role file), keyed by branch because the trail starts before the PR exists, so it outlives the owner and no other run or repo shares it. The owner pushes and starts the trail soon after it starts, then pushes after every unit worth keeping. A local owner writes the trail itself. A cloud owner cannot reach the store, so it posts each trail row and each new child's id in a PR comment marked `<!-- autopilot-trail -->`, and you copy them into its directory at every drain and tick, by comment id, so a second copy changes nothing. Copy a trail comment only when the owners' account wrote it on the PR you assigned that owner, for the same reason as reports. Whoever spawns a subagent records it with its state and a stuck-after runtime from past runs of its kind, so it can be probed if its parent dies. You record your owners in `autopilot/<run-slug>/children.tsv`, with each owner's `delegate_task` taskId and thread id, so a restarted root can find them. A local owner records its children in the `children.tsv` beside its trail, with taskId and thread id. A cloud owner has no T3 tools, so it records its PR and branch instead. `task_status` reads only tasks the calling thread created, so probe your own owners with it, a recorded child with `t3_thread_read` on its thread id, and cloud work by its PR and branch. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, on the counterpart of the code author's family (the Counterparts list in the role file). Fan out independent verifiers at the code-ready SHA per the **swarm** skill. They re-run the gates, prove the load-bearing behavior live on the real surface through the project's verify skill, which each brief names, and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's receipts, because no lane trusts a claim it has not checked.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward, with a red test across every site with the same defect. A defect trunk shows without the PR is recorded against trunk and does not gate the PR, but one the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, arm the hourly wake per the Waking and polling section of the role file (a `schedule_task` interval whose `scheduledTaskId` you keep and delete when no delegated work is left) to audit until no delegated work is left, because long runs drift and agents stall silently. Each tick re-reads this playbook from trunk (`git -C ~/lim-v2/code/liminal-plugins/pstack-lim fetch -q && git -C ~/lim-v2/code/liminal-plugins/pstack-lim show origin/lim:pstack/skills/poteto-mode/playbooks/autopilot-full.md`) and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it, because drift is a gap in the record, not a stall. It copies each cloud owner's marked PR comments into that owner's store directory by comment id, after the same author and PR checks, then probes every agent, down to the leaf lanes (`task_status` on each owner you spawned, `t3_thread_read` on each thread id in the `children.tsv` files under this run's `autopilot/<run-slug>/` in the pstack store, `t3_thread_list`, and each cloud owner's PR and branch), and judges each by its side effects, because status text and summaries can hide a stuck child. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.
8. **Close out from the plan.** When the queue has a plan, file its owed list per poteto-mode's close-out rule, as a few tickets grouped by body of work, and none for its decided-no items, and name every scope cut in the reply. A finding deferred during the run goes onto one of those lists when it is deferred, so close-out reads the plan instead of the PR threads.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, the tickets filed from the owed list, and every scope cut, with links to each PR and the trails.
